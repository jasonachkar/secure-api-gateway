# Security Controls

Maps implemented controls to the concerns they address, each citing the file that
actually implements it. For attack-scenario reasoning (why these controls exist), see
[`THREAT_MODEL.md`](THREAT_MODEL.md); for the OWASP API Top 10 walkthrough with code
snippets, see [`owasp-api-top10.md`](owasp-api-top10.md).

## Authentication

| Control | Implementation | Notes |
|---|---|---|
| Password hashing | `src/lib/crypto.ts` (bcrypt, `BCRYPT_ROUNDS`, default 12) | Constant-time verification |
| JWT access + refresh tokens | `src/middleware/auth.ts`, `src/modules/auth/auth.service.ts` | HS256 in the Azure deployment; RS256 supported (file-based keys) |
| Refresh token rotation + reuse detection | `src/modules/auth/auth.service.ts` (`refresh()`), `token.store.ts` | Reuse revokes the entire token **family**, not just the reused token |
| Access-token revocation | `src/middleware/auth.ts` (`requireAuth` checks `tokenStore.isRevoked`), `auth.service.ts` (`revokeAccessToken`) | Closed in this modernization pass - was previously a `// TODO`, access tokens only relied on expiry |
| Account lockout | `src/modules/auth/auth.service.ts` (`LockoutManager`) | Redis-backed, keyed by username+IP, `MAX_LOGIN_ATTEMPTS`/`LOCKOUT_DURATION` |
| Scoped API keys | `src/modules/apikeys/` | SHA-256-hashed at rest, raw value shown exactly once at creation, per-scope authorization |

## Secrets management

| Control | Implementation | Notes |
|---|---|---|
| No secrets in source | `.env.example` documents names only; real values via `.env` (gitignored) locally, Key Vault in Azure | |
| Production fail-fast on placeholder secrets | `src/config/env.ts` (`superRefine`, `KNOWN_PLACEHOLDER_SECRETS`) | Refuses to boot with a known example `COOKIE_SECRET`/`JWT_SECRET` when `NODE_ENV=production` |
| Key Vault-backed runtime secrets | `terraform/main.tf`, `terraform/modules/container-app` | `cookie-secret`, `jwt-secret` generated by Terraform (`random_password`) and written to Key Vault directly - no manual seeding needed for the app to boot |
| Least-privilege secret access | `terraform/modules/container-app` (user-assigned identity, "Key Vault Secrets User" role only) | The running app can read secrets, not manage the vault |
| Secret rotation path | `terraform/README.md#rotating-secrets` | `terraform taint` + apply for generated secrets, `az keyvault secret set` for manually-seeded ones |

## Cross-origin requests

| Control | Implementation | Notes |
|---|---|---|
| Explicit CORS origin allowlist | `src/app.ts` (`@fastify/cors` registration), `env.security.corsOrigins` | Fixed in this pass - the CORS plugin was hardcoded to `origin: true` (reflect *any* origin, with `credentials: true`), completely bypassing the `CORS_ORIGIN` allowlist that `env.ts` validated but never actually applied. ## Compliance mapping

A directional mapping, not a certification claim - useful for orienting a reviewer, not
for an actual audit.

| Area | OWASP API Top 10 (2023) | Zero-trust principle | Control |
|---|---|---|---|
| Object-level auth | API1 (BOLA) | Verify explicitly | Resource ownership check (`reports.service.ts`) |
| Auth | API2 (Broken Authentication) | Verify explicitly | JWT + rotation + reuse detection + lockout |
| Property-level auth | API3 | Least privilege | Response allowlisting (`sanitizeReport`) |
| Resource consumption | API4 (Unrestricted Resource Consumption) | Assume breach | Rate limiting (global/user/apikey), body/timeout limits |
| Function-level auth | API5 (BFLA) | Verify explicitly | RBAC on every admin/write route |
| Business flow abuse | API6 | Assume breach | Threat-intel scoring, account lockout |
| SSRF | API7 | Least privilege / assume breach | Allowlist + DNS pinning + circuit breaker |
| Security misconfiguration | API8 | Verify explicitly | Prod fail-fast config validation, security headers |
| Inventory management | API9 | - | OpenAPI spec (`openapi/openapi.yaml`), Swagger UI (dev only) |
| Unsafe API consumption | API10 | Least privilege | SSRF controls apply symmetrically to what the gateway itself consumes |

## Roadmap

Documented honestly as not-yet-implemented, rather than partially faked:

- **JWT key rotation / JWKS** — currently a single static signing key (HS256 secret or
  RS256 key pair). A real rotation path needs multi-key support (`kid` claim, a JWKS
  endpoint or Key-Vault-backed multi-key lookup) so old tokens keep validating during a
  rotation window. Not implemented.
- **OpenTelemetry distributed tracing** — currently request-ID correlation
  (`src/lib/requestContext.ts`) plus Application Insights via its Node SDK, not full
  OTel spans/exporters. Would give proper distributed traces across the
  gateway→upstream boundary.
- **mTLS to upstream services** — the SSRF/DNS-pinning controls address this
  deployment's actual outbound trust problem (untrusted destination); mTLS would add
  mutual authentication for upstream services that support client certificates, which
  none of the demo upstreams do today.
- **Cryptographically anchored (not just chained) audit log** — the hash chain detects
  tampering but doesn't prevent a full rewrite by someone with direct store access.
  A real implementation would periodically publish the latest hash to independent,
  append-only storage (or a public transparency log).
- **MFA / WebAuthn** — login is single-factor (password) today.
- **Signed container image provenance** — CI builds and scans the image but doesn't
  sign it (e.g. Sigstore/cosign) or attach SLSA provenance.
